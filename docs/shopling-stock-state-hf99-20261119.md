# Shopling stock-state HF99 — 판매종료(E) 제외 처리

## 운영 결정

- Shopling 상품상태 `E`는 공식 API 기준 `판매종료`다.
- 판매종료 GOODS KEY는 판매중 전환과 품절 처리 모두에서 API 변경과 A21 전송을 하지 않는다.
- 같은 B코드 안의 나머지 GOODS KEY는 기존처럼 한 건씩 상태·수량을 재조회하고 직렬 전송한다.
- 전부 판매종료인 B코드는 실패·재시도 대상이 아니라 `전송 없이 처리 완료`로 끝낸다.
- `A(대기중)`, `D(판매중지)`, `Z(삭제)` 등 E 이외의 비정상 상태는 임의로 건너뛰지 않고 기존 안전 차단과 상세 원인 표시를 유지한다.

## 실제 사건 근거

- 공식 Shopling API 매뉴얼의 `sale_status` 정의는 `A:대기중, B:판매중, C:품절, D:판매중지, E:판매종료, Z:삭제`다.
- 실제 `BAF3-3` 조회에서 16개 GOODS KEY 중 14개는 상품상태 C, 2개(`108854`, `108855`)는 상품상태 E였다.
- 화면에서 보인 `판매중`은 해당 행의 옵션상태였고, 상품 미리보기의 판매상태는 판매종료였다. 따라서 옵션상태 B를 근거로 상품상태 E를 되살리면 안 된다.

## 구현 경계

- 서버는 각 GOODS KEY의 현재 상품상태를 먼저 읽고 E이면 쓰기 함수와 전송 계획 생성 전에 제외한다.
- 응답에는 제외된 GOODS KEY, 제외 건수, 처리 가능한 GOODS KEY가 없는지 여부를 별도로 남긴다.
- HF99 확장 v0.6.59는 처리 대상이 0건인 정상 응답을 실패로 오판하지 않고 A21을 열지 않은 성공 영수증을 남긴다.
- 처리 가능한 GOODS KEY가 하나라도 있으면 제외된 E는 버리고 나머지만 기존 HF96 팝업 소유권·파란 전송 영수증 절차로 진행한다.

## 검증

- HF99 전용 회귀: 전부 E이면 A21 시작 0회·성공 영수증, E와 정상 상품 혼합이면 정상 GOODS KEY만 A21 작업에 포함됨.
- HF98/HF99 상태 설명 회귀: 공식 A/D/E 라벨과 E 자동 제외 안내 확인.
- HF99 직접·현재 운영 회귀 58개와 수정된 Shopling 이력 회귀 167개, TypeScript, 변경 파일 ESLint 통과.
- Next.js 125개 페이지 프로덕션 빌드 통과(`--webpack`; 기본 Turbopack은 공유 node_modules junction을 프로젝트 밖 심볼릭 링크로 거부한 환경 문제).
- 로컬 빌드 서버의 HF99 검증 응답: v0.6.59, ZIP 275,074 bytes, ZIP SHA-256 `d517359dc4af96f0fa8ae7e691ca1aca18fa1489f6c2a84d089de000e49f310d`, OPS SHA-256 `952432441fcb4e034855386414a10a2e1ee2586550c8f4d408533c8f6899d04a`.
- 전체 저장소 테스트는 현재 main의 기존 비관련 실패가 있어 전체 녹색 기준으로 사용하지 않았다. 이번 변경 대상과 연결 회귀는 별도로 모두 통과했다.

## 배포 후 실제 확인

1. Commerce OS에서 v0.6.59 확장을 내려받아 기존 확장 폴더를 교체한다.
2. Shopling 로그인과 Commerce OS `자동화 연결됨 · v0.6.59`를 확인한다.
3. `BAF3-3`처럼 E와 정상 상태가 섞인 B코드 1건으로 실행한다.
4. E GOODS KEY는 전송 목록에서 빠지고 나머지만 Shopling 접수되는지 확인한다.
5. 이 실제 접수 확인 전에는 운영 성공을 확정하지 않는다.
