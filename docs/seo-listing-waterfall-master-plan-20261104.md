# SEO 상품 물갈이 전체 기획안

기준일: 2026-11-04  
현재 단계: **4단계 — 관리대상 기준선 재대사와 생애주기 식별자 정합성 감사**

## 1. 사업 목적

Shopling에 등록한 SEO 상품을 오래 방치하지 않고, 실제 판매 근거에 따라 유지·보호·교체하는 운영 체계를 만든다.

- 60일 동안 판매가 확인되지 않은 상품은 검증된 절차로 노출을 종료한다.
- 90일 휴지 뒤 제목만 바꾸는 재사용이 아니라 새 SEO RUN과 새 상품코드 6개로 다시 시험한다.
- 판매가 한 건이라도 확인된 상품은 보호한다.
- 최대 3회의 검증된 노출 기회에도 판매가 없으면 단종 후보로 올린다.
- 상품 마스터와 B코드 원본은 보존하고 Shopling의 검증된 listing만 교체한다.

이 프로젝트의 직접 고객은 현재 내부 상품 운영자다. 수익 가설은 `수동 관리시간 절감 + 판매 가능 상품의 노출 유지 + 무판매 슬롯의 회전율 개선`이다. 아직 물갈이가 추가 매출·이익을 만들었다는 실증은 없으며, 1개 상품 Canary부터 비용과 판매 기여를 측정한다.

## 2. 확정 운영 정책

한 상품은 `도매1~4, 소매1~2`의 6개 Shopling 상품코드를 한 세트로 사용한다.

```text
신규/재등록 완료 readback
  → 60일 검증 노출
  → 판매 1건 이상: PROTECTED
  → 판매 0건: 6개 품절 → 품절 readback → 6개 삭제 → 삭제 readback
  → 90일 COOLDOWN
  → 새 SEO RUN + 새 selfCode/goods_key 6개 생성 및 마켓전송
  → 최대 3회 반복
  → 3회 모두 무판매: RETIRE_CANDIDATE
```

다음 상황은 노출 기회를 소비하지 않고 `EXCEPTION/확인 필요`로 보낸다.

- 판매중 상태, 판매량, 마켓전송 또는 삭제 결과를 읽지 못함
- 6개 코드가 일부만 존재하거나 프로필·B코드가 충돌함
- 응답이 불명확한 외부 쓰기, 진행 중인 작업 또는 중복방지키 충돌
- Shopling 상품 DB나 필수 마켓의 최신 용량 근거가 부족함

## 3. 안전 경계

- 자동 실행은 내부 판단과 readback이 먼저다. Shopling·마켓 쓰기는 단계별 별도 승인 전까지 잠근다.
- 외부 쓰기는 한 상품의 6개 코드를 하나의 작업 단위로 계획하고, 각 단계 뒤 실제 상태를 다시 읽는다.
- 성공 여부가 불명확한 쓰기는 자동 재시도하지 않고 `confirm_needed`로 멈춘다.
- 상품 마스터, B코드, 옵션 원장은 삭제하거나 덮어쓰지 않는다.
- Shopling 자체관리코드와 정식 숫자형 옵션 B코드를 섞지 않는다.
- 신규등록은 최신 Shopling 상품 DB readback이 24시간 이내이고, 안전 여유 12코드를 남길 때만 허용한다.
- 필수 마켓 슬롯은 합산하지 않고 가장 작은 잔여 슬롯을 전체 배치 상한으로 사용한다.
- 한도 증거가 불완전하면 신규등록 0개, 품절·삭제 0개로 실패 안전하게 끝낸다.

### 4단계 — 관리대상 기준선·식별자 정합성 감사 `현재 진행 중`

목표는 편입 숫자가 아니라 각 상품의 6개 프로필과 `goods_key`가 현재 Shopling 카탈로그·마켓 원장·저장된 lifecycle 행에서 정확히 같은 쌍인지 증명하는 것이다.

이번 변경:

- 프로필 6개가 단순히 같은 집합인지만 보지 않고 각 `goods_key ↔ profile` 쌍을 정확히 비교
- 한 goods key에 partner code가 복수면 같은 프로필 접미사여도 충돌 처리
- 이미 편입된 상품만 대상으로 하는 인증된 read-only 감사 action 추가
- 감사와 apply 동시 요청을 서버에서 차단
- 6,072 / 10,000일 때 안전 신규 세트 652개 계산 회귀 테스트 추가

Production read-only 감사 결과:

- 최초 전체 lifecycle 범위는 256개로 과대 포함되어 출처 범위를 교정했다.
- 온보딩 출처와 legacy 격리상품을 구분한 현재 운영 감사 대상은 179개다.
- 이전 전량 스캔에서는 127개보다 52개 많은 원인을 설명하지 못해 127개를
  확정 기준선으로 사용하지 않았고, 아래 exact goods_key 조회로 재검증했다.
- PR #1668부터 등록일 전체 스캔 대신 lifecycle에 저장된 Shopling `goods_key`
  652개만 공식 `prod_id` API로 정확조회한다. 전체 9,874행 스캔이 652개
  요청·1,144개 옵션행 응답으로 축소됐다.
- 정확조회 결과는 `0 통과 / 179 확인 필요`, 현재 Shopling 카탈로그 매칭
  127개, 미매칭 52개다. 이로써 이전 계획값 127개는 강제한 숫자가 아니라
  현재 goods_key와 연결된 상품 수로 재확인됐다.
- 미매칭 52개는 현재 카탈로그 누락 51개와 launch option B코드 누락 1개다.
  lifecycle 원장에는 남아 있지만 현재 관리 세대로 간주하지 않는다.
- 현재 매칭 127개의 확인 필요 사유는 정체성 충돌 72개, 6개 프로필 세트

### 5단계 — 기존 코드 품절·삭제 Canary `다음 단계, 별도 승인 필요`

- 정확히 60일 검증 무판매인 상품 1개만 선택
- 6개 코드의 최신 판매중 상태, 판매 0건, 마켓 원장, 중복방지키를 실행 직전 재확인
- `품절 6개 → readback 6/6 → 삭제 6개 → readback 6/6` 순서로 실행
- 응답 불명확, 일부 성공, 식별자 불일치가 있으면 즉시 멈추고 자동 재시도하지 않음

완료 조건: 상품 마스터 보존, 의도한 6개만 삭제, 외부 부작용 0건, 감사 로그와 readback 영수증 보존.

### 6단계 — 90일 휴지 관리 `Canary 이후`

- 삭제 readback 완료 시각부터 90일 계산
- 휴지 중에는 새 RUN·새 코드 생성 금지
- 종료 직전과 종료 시각의 경계 테스트

### 7단계 — 새 SEO RUN·새 코드 6개 등록 Canary `별도 승인 필요`

- 휴지 종료 후 생성된 새 SEO RUN만 허용
- 이전 6개 삭제 readback, 최신 상품 DB 여유, 필수 마켓 슬롯을 다시 확인
- 새 selfCode/goods_key 6개 등록 후 Shopling 실상품과 마켓전송을 6/6 readback
- 성공 전에는 노출 시도 횟수를 소비하지 않음

### 8단계 — 제한 배치 확대 `Canary 2종 성공 후`

- 처음에는 1일 1상품, 이후 실패율과 운영부담을 보고 소규모로 확대
- Shopling DB와 필수 마켓 중 가장 작은 안전 슬롯을 상한으로 유지
- 확인 필요·진행 중·보호·휴지·단종 후보는 신규 작업에서 제외

확대 조건: 중복·오삭제 0건, readback 누락 0건, 사람이 처리해야 하는 예외율이 합의한 수준 이하.

### 9단계 — 3회 수명주기와 월간 운영판 `운영 완성`

- 노출 1~3회 성과, 보호 상품, 휴지, 단종 후보, 예외함을 한 화면에 표시
- 코드 사용량, 등록 성공률, 판매 전환, 처리 시간, 외부 오류를 월별 집계
- `RETIRE_CANDIDATE`는 자동 원본 삭제가 아니라 사람이 판단하는 후보로 유지

### 10단계 — Auto 전환 여부 결정 `최종 별도 승인`

- 충분한 Canary·제한 배치 증거가 쌓인 뒤에만 자동 외부 쓰기 검토
- 실패 비용과 매출 기여가 불분명하면 Shadow/승인형 운영을 유지
- 자동화 자체가 목표가 아니라 수익성과 운영 안정성이 목표다.

## 6. 사업 검증 지표와 중단 기준

초기 1개 Canary와 제한 배치에서 아래를 측정한다.

- 무판매 슬롯 한 세트를 교체하는 총 운영시간과 실패 복구시간
- 신규 노출 60일 동안의 주문수, 매출, 공헌이익
- 보호 전환율과 1·2·3회차별 판매 전환 차이
- 상품코드 6개당 유지비용과 남은 Shopling 용량
- 오삭제, 중복등록, readback 누락, 수동 확인 필요 비율

다음 중 하나면 확대를 중단하고 수정 또는 전략 전환한다.

- 의도하지 않은 상품이나 코드가 한 건이라도 변경됨
- 6개 원자 단위의 readback을 안정적으로 증명하지 못함
- 예외 처리 비용이 수동 운영 절감보다 큼
- 충분한 표본에서도 물갈이 상품의 공헌이익 개선이 나타나지 않음
- Shopling/마켓 정책 또는 용량 때문에 지속 가능한 회전이 불가능함

## 7. 바로 다음 실행 순서

1. 통과한 현재 상품 48개의 감사 영수증을 내부 원장에 별도 보존할 설계를 확정한다.
2. 이전 세대/누락 52개를 현재 관리대상에서 내부적으로 격리할 계획을 만들고
   대상 goods_key가 현재 상품과 겹치지 않는지 다시 확인한다.
3. 마켓 원장 미완성 9개는 Shopling 6개와 lifecycle 6개가 정확히 일치할 때만
   내부 원장 복구 후보로 올리고, 나머지 70개 실제 데이터 예외와 분리한다.
4. 내부 Shopling 용량 readback 6,072를 재확인한다.
5. 내부 원장 교정 뒤 read-only 감사를 다시 실행해 통과 수와 부작용 0건을 확인한다.
6. 60일 무판매 조건을 충족한 실제 후보가 생기면 사용자에게 상품명·B코드·6개 goods key·영향 범위를 제시한다.
7. 사용자가 그 1개 Canary의 외부 품절·삭제를 명시적으로 승인한 뒤에만 5단계로 이동한다.

현재 사용자가 추가로 할 일은 없다. 48개 통과 영수증 보존과 52개 이전 세대
내부 격리 설계를 먼저 완료해야 다음 승인 판단이 가능하다.
