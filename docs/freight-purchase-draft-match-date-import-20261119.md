# 배대지 바코드 발주초안 우선매칭·신청일 가져오기 (2026-11-19)

## 목표

- 발주차시에서 바코드 화면으로 이동했을 때 신청서 품목의 오픈마켓 주문번호를 선택 발주초안과 먼저 대조해 B코드·모델번호·모델명을 입력한다.
- 발주초안에 후보가 없을 때만 기존 커머스OS 상품마스터의 1688 offer ID·중국 옵션 정확매칭을 사용한다.
- 신청서 번호 직접 입력뿐 아니라 온돌패스 신청일 시작일·종료일로 신청서 목록을 찾고 같은 순차 가져오기·분석 흐름을 실행한다.

## 확인한 원인과 실제 데이터

- 기존 최종 바코드 URL은 `draft`를 잃고 브라우저 `sessionStorage`에만 의존해 선택 발주초안이 서버 자동매칭에 전달되지 않았다.
- 신청서 673626의 상품마스터 미매칭 2건은 발주초안에 이미 존재했다.
  - 주문번호 `3317016685189009453` → `BBF8-1` / `AAA367` / 차량용 소변기
  - 주문번호 `3316586270196027099` → `BBE6-2` / `AAA507` / 투명 플라스틱 서랍형 수납함
- 실제 온돌패스 `2026-11-18~2026-11-18` 신청일 검색 결과는 `673626, 673624, 673623, 673622` 4건이었다.

## 구현 계약

1. 월간 연결 페이지가 선택 `draftId`를 최종 바코드 URL에 보존한다.
2. 서버 매칭 API가 같은 인증 범위 안에서 발주초안을 읽는다.
3. 오픈마켓 주문번호가 하나의 발주초안 라인과 일치하면 옵션 표기 차이가 있어도 그 라인의 B코드·모델을 적용한다.
4. 같은 주문번호 후보가 여러 개면 offer ID, 중국 옵션, 수량 순으로 유일 후보만 적용한다. 동률은 확인 필요로 남기며 상품마스터로 덮지 않는다.
5. 발주초안 후보가 전혀 없을 때만 상품마스터 정확매칭으로 보완한다.
6. 날짜 조회 확장은 온돌패스 신청현황의 GET 조회 주소만 열며 체크박스·신청서 내용은 변경하지 않는다.
7. 신청일 범위·신청서 번호·행 날짜·중복·500건 한도를 검증한 뒤 기존 한 건씩 순차 상세 가져오기를 재사용한다.

## 검증 증거

- 실제 실패 2건 회귀 픽스처에서 발주초안 주문번호로 `BBF8-1`, `BBE6-2` 매칭 확인
- 같은 주문번호 중복 후보를 임의 지정하지 않는 실패 차단 확인
- 상품마스터 fallback 유지 확인
- 실제 온돌패스 행 구조 기반 날짜 추출기와 4개 신청번호 검증 확인
- 확장 권한은 `tabs`, `scripting`만 유지하고 쿠키·별도 fetch·페이지 클릭 없음 확인
- 로컬 Chrome에서 실제 신청서 `673626`의 9개 품목·9개 이미지를 브리지로 불러와 파서와 화면 적용까지 확인
- 로컬 서버에는 운영 상품마스터 연결 비밀값이 없어 9개 B코드 최종 매칭은 운영 배포 후 확인 대상으로 분리
- 집중 자동 테스트 58개 통과
- 변경 파일 ESLint, 전체 TypeScript 검사, Next.js 프로덕션 빌드 통과

## 배포 후 확인

- 운영 발주차시 3단계에서 다시 진입해 최종 URL에 `draft`가 유지되는지 확인한다.
- 신청서 673626 분석 후 9개 품목 모두 B코드·모델번호·모델명이 입력되는지 확인한다.
- 브리지 v0.2.0을 설치/새로고침하고 `2026-11-18` 1일 조회가 4개 신청서를 찾는지 확인한다.
