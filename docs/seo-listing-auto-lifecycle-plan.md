# SEO 상품 자동등록·물갈이 — Shadow v1 / 새 코드 물갈이

## 목표

`/seo-bulk-cloud`를 사람이 등록 대상을 매번 체크하는 업로드 화면에서, 운영자는 월간 성과와 예외만 확인하는 상품 포트폴리오 자동화 화면으로 발전시킨다.

기존 기능은 유지한다.

- 샵플링 일괄 대량등록 및 마켓전송
- 등록 실패 확인과 오류 체크포인트 재실행
- SEO RUN 생성·보관·복구

## 확정 정책

- 정상 판매중 readback이 확인된 시점부터 60일을 한 번의 노출 기회로 계산한다.
- 노출 중 1건이라도 판매되면 `PROTECTED`로 유지한다.
- 60일 동안 판매가 0이면 Shopling 품절 및 삭제전송을 계획하고, 삭제 readback 완료 후 90일 휴지한다.
- 휴지 종료 후 새 SEO RUN을 준비하고 새 Shopling `goods_key` 6개를 생성해 다시 등록·마켓전송한다. 이전 6개 코드는 60일 무판매 판정 뒤 이미 품절·삭제 readback까지 끝난 상태여야 한다.
- 최대 3회의 검증된 노출 기회를 준다.
- 3회 모두 무판매인 상품만 `RETIRE_CANDIDATE`로 올린다. 상품 마스터 원본은 삭제하지 않는다.
- 기술 오류, 마켓 미노출, 판매중 readback 부재는 기회를 소비하지 않고 예외로 보낸다.
- 상품별 계절성은 추정하지 않는다. 60일 노출 + 90일 휴지가 여러 시기를 통과하게 하는 단순 정책으로 대체한다.

## Shadow v1 안전 경계

이 단계는 판단과 화면만 제공하며 Shopling 또는 마켓에 쓰지 않는다.

- 자동 실행은 코드에서 `false`로 고정한다.
- 데이터베이스 정책 기본값도 `enabled=false`, `mode=shadow`다.
- 실행 스케줄/dispatcher를 등록하지 않는다.
- 마켓별 최대 등록수·현재 등록수·진행중 수량·안전 여유를 모두 확인한다.
- 필수 마켓 한 곳이라도 값이 없거나 오류이거나 24시간보다 오래되면 물갈이·삭제 배치를 차단한다. 신규 등록은 기존 송신기의 검증된 동시 처리 상한인 최대 3개로 제한하되, Shopling 상품 DB 사용량이 미확인·오래됨·한도 초과이면 0개로 완전히 차단한다.
- 여러 마켓에 함께 보내므로 남은 슬롯을 더하지 않고 가장 작은 필수 마켓 슬롯을 배치 상한으로 사용한다.
- 한 상품의 여러 SEO RUN 중 최신 RUN 하나만 자동선택 후보가 될 수 있다.
- 불확실한 외부 쓰기는 재시도하지 않으며 향후 `confirm_needed`로 분리한다.

### 마켓 한도 readback 계약

- 현재 상품그룹 레지스트리의 29개 마켓 계정만 수집 대상으로 허용한다.
- 수집기가 일부 계정을 확인하지 못해도 서버가 29개 전체 스냅샷을 만들고, 누락 계정은 `unknown`으로 저장한다. 따라서 누락을 0건으로 오해하지 않는다.
- 스냅샷은 owner와 UUID로 식별하며, 24시간을 지난 증거와 5분보다 미래인 증거는 받지 않는다.
- 29개 행을 한 RPC에서 원자적으로 반영하고, 더 오래된 스냅샷은 최신 값을 덮지 못한다.
- 저장 타임아웃은 성공·실패가 불명확한 쓰기다. 같은 스냅샷 29개를 한 번 재조회해 전부 일치할 때만 성공으로 대사하며, 불일치하면 `confirm_needed`로 끝내고 쓰기를 자동 재시도하지 않는다.
- 이 POST는 Commerce OS 내부 증거 저장만 수행한다. Shopling 또는 마켓에는 쓰지 않는다.

## 데이터 소유권

- 상품의 기준 진실: 기존 Product Master / product launch item
- SEO 등록 준비: 기존 `seo_run_jobs`
- Shopling/마켓 식별자: listing lifecycle ledger의 `goods_key`, `market_listing_id`
- 물갈이 ledger는 상품 원본을 복제하거나 삭제하지 않는다.

## 상태 흐름

`READY → LIVE → PROTECTED`

또는

`READY → LIVE → COOLDOWN → READY → LIVE → COOLDOWN → READY → LIVE → RETIRE_CANDIDATE`

외부 증거가 부족하거나 기술 실패가 발생하면 `EXCEPTION`으로 보낸다.

## Shadow v1 인수 조건

1. `/seo-bulk-cloud` 상단에 자동등록·물갈이 현황이 보인다.
2. 기존 일괄등록·마켓전송·오류 재실행 컨트롤이 그대로 존재한다.
3. 59일에는 유지하고 정확히 60일에 무판매 물갈이를 계획한다.
4. 휴지 종료 직전에는 재등록하지 않고 정확한 종료 시점부터 재등록 후보가 된다.
5. 3번째 무판매 노출 뒤에는 재등록이 아니라 단종 후보가 된다.
6. 판매 1건 이상이면 보호한다.
7. 기술 오류와 미검증 노출은 횟수를 늘리지 않는다.
8. 마켓 한도 readback이 없거나 24시간보다 오래되면 신규 등록을 최대 3개 제한 모드로 계산하되, Shopling 상품 DB readback이 없거나 24시간보다 오래되거나 한도에 도달하면 신규 등록은 0개로 잠근다.
9. 필수 마켓 슬롯 20개와 5개를 합쳐 25개로 보지 않고 5개만 안전 배치한다.
10. 현황 API의 `prepare_scheduled_run` POST는 owner 범위에서 오늘 실행 대상을 다시 계산만 하며 외부 마켓에는 쓰지 않는다. 별도 한도 readback POST는 인증된 owner의 29개 증거만 원자 저장·재조회한다.
11. 90일 휴지 뒤 재도전은 기존 RUN이나 기존 `goods_key`를 재사용하지 않는다. 이전 6개 코드 삭제 readback, 6개 고유 마켓·코드, 휴지 종료 뒤 생성된 새 SEO RUN, Shopling 새 코드 6개 슬롯이 모두 확인돼야만 신규등록 계획에 들어간다.

## 2026-10-28 원클릭 운영 연결

- `/seo-bulk-cloud` 첫 화면에서 오늘 등록 가능, 노출 중, 판매 보호, 휴지, 단종 후보, 확인 필요를 한눈에 본다.
- 실행 순서는 `재고·판매·마켓 한도 재확인 → 생애주기 안전대상 선택 → 기존 Shopling 업로드·마켓전송 오케스트레이터 인계`다.
- 사용자는 재고 동기화가 끝난 뒤 `오늘 자동운영 1번 실행`만 누른다. 기존 등록 성공 후 마켓전송이 남은 최신 묶음도 같은 실행에 합친다.
- 최신 RUN만 사용하고, `PROTECTED`, 노출 중, 휴지 중, 단종 후보, 확인 필요 상품은 신규 자동등록 대상에서 제외한다.
- 필수 마켓 한도 증거가 없거나 오래되면 물갈이·삭제는 계속 차단한다. 다만 사용자가 한도 숫자를 직접 관리하지 않도록, 신규 등록만 기존 송신기의 검증된 동시 처리 상한인 최대 3개로 제한해 실행한다. 한도 증거가 정상 수집되면 가장 작은 필수 마켓 슬롯을 다시 사용한다.
- 문제 해결용 신규 등록 전용·마켓전송 재개 버튼은 접힌 보조 영역에 유지한다.
- 품절·삭제 예정 수량은 화면에 표시하지만 실제 품절·삭제는 계속 잠근다. 소수 상품 Canary와 삭제 readback 검증 전에는 자동 실행하지 않는다.
- 화면은 `SEO 준비 → 오늘 실행 → 처리 중 → 등록 완료 → 판매 보호` 흐름과 검증 판매·등록 실패·재도전 준비 수를 한눈에 보여준다.
- 자동 수명주기 현황 조회가 일시 실패해도 기존 등록·마켓전송 복구 기능은 함께 멈추지 않는다.
- 검증: 정책·경계·계약 테스트, TypeScript, 변경 파일 ESLint, production build를 통과했고 로컬 브라우저에서 요약판과 원클릭 버튼 순서를 확인했다.

## 다음 단계와 실제 운영 전 증거

Shadow v1 이후 아래 순서로만 확장한다.

1. Shopling/마켓별 최대 등록수와 현재 등록수를 읽는 로컬 collector 연결(제공받은 Shopling API 문서에는 계정별 최대 등록 한도 필드가 없으므로, 그 전까지 신규 등록 3개 제한 모드를 사용)
2. 상품별 실제 판매중 시작일, 판매량, 품절·삭제 완료 readback 연결
3. Shadow 예상과 사람이 확인한 결과의 대사
4. 소수 상품·소수 계정 Canary 등록
5. 등록/품절/삭제 각각의 식별자 readback 및 중복 방지 검증
6. 월간 요약과 예외함 운영 검증
7. 별도 소유자 승인 후에만 Auto 전환

Production migration 적용과 실제 마켓 쓰기 활성화는 이 문서 작성만으로 승인된 것이 아니다.

## 2026-10-29 내부표 자동 대사 연결

- 최근 성공 SEO RUN의 정확한 Shopling `goods_key` 6개를 `도매1~4, 소매1~2`와 대조한다.
- 마켓전송 원장, 현재 Shopling 판매상태 readback, Product Master B코드별 판매근거를 함께 확인한다.
- 세 근거가 모두 맞는 신규 행만 `LIVE`로 시작하고, 등록 뒤 판매가 한 건이라도 확인되면 6개 채널 모두 `PROTECTED`로 둔다.
- `legacy_ignored`, 현재 품절·삭제·미확인, 48시간을 넘긴 판매근거, 6채널 식별자 누락은 `EXCEPTION`으로 보류하며 시도 횟수를 소비하지 않는다.
- 최초 `LIVE` 시작일은 과거 등록일을 추정하지 않고 최초 현재 판매중 readback 시각으로 잡는다. 따라서 검증하지 않은 과거 노출일을 60일에 포함하지 않는다.
- 기존 수명주기 행은 이 bootstrap이 덮어쓰지 않는다. 원클릭 준비 시 비어 있는 내부표만 채우며 Shopling/마켓 외부 쓰기는 하지 않는다.
- 운영 전수조사 결과: 최신 성공 상품 71개 모두 6개 채널·상품출시 항목·B코드 판매근거와 연결됐다. 마켓 등록 완료가 직접 입증된 상품은 50개이고, 나머지 21개는 예전 `legacy_ignored` 기록이라 자동 보류 대상이다. 최종 LIVE/PROTECTED 수는 현재 Shopling 판매상태 readback 뒤 확정한다.

## 남은 기획 순서

완료된 기반:

- Production bootstrap과 대사를 완료했다. 71개 상품의 6개 채널, 총 426개 내부 행을 만들었고 `LIVE 297 / PROTECTED 12 / 확인 필요 117`로 확인했다.
- 판매가 확인된 상품 2개는 6개 채널 모두 보호되며, 검증된 판매 건수는 12건이다.
- 화면은 `판매 보호 2 / 검증된 판매 12 / 확인 필요 21개 상품 / 품절·삭제 예정 0`을 표시한다.
- 외부 품절·삭제는 계속 잠겨 있다.

현재 개발·검증 중:

1. 매일 1회 현재 판매중 상태와 48시간 이내 최신 판매근거를 읽어 검증된 노출일만 1일 늘린다. 읽기 실패일과 같은 날의 중복 실행은 늘리지 않는다.
2. 검증된 노출일이 정확히 60일이고 판매가 0인 행만 내부 Shadow `SOLD_OUT`·`DELETE` 예정표에 넣는다. 실제 Shopling/마켓 쓰기는 하지 않는다.
3. 새 일일 작업은 먼저 dispatcher에 `enabled=false`로 배포하고 Production 수동 대사 후 별도 migration으로 하루 1회만 활성화한다.

Production 수동 대사 결과:

- `LIVE / PROTECTED` 309행(52개 상품)을 읽었고 Shopling 현재상태는 309행 모두 판매중 `B`였다.
- 같은 서울 날짜의 재실행이라 노출일·이벤트는 중복 증가하지 않았고, Shadow 품절·삭제 예정도 0건이었다.
- 기존 상태 `LIVE 297 / PROTECTED 12 / EXCEPTION 117`이 그대로 유지됐다.
- 외부 마켓 쓰기 0건을 확인한 뒤 하루 1회 dispatcher 활성화 migration을 추가했다.

## 2026-10-30 Shopling 상품 DB 1만 개 한도 안전장치

- Shopling 요금제의 상품 DB 최대치는 10,000코드이며 확인 당시 누적 사용 수는 11,113코드였다. 따라서 새 상품코드를 만드는 SEO 등록은 즉시 차단한다.
- 한 SEO 상품은 도매1~4·소매1~2의 상품코드 6개를 사용한다. 안전 여유 12코드를 별도로 남기고 `(최대-사용-12) ÷ 6`의 정수 부분만 신규 상품 수로 허용한다.
- 위탁상품을 삭제했다는 사실만으로 여유가 생겼다고 보지 않는다. Shopling 요금제 화면의 최신 사용 수가 실제로 낮아진 readback만 반영한다. `누적` 수치가 삭제 후에도 줄지 않으면 신규 코드는 계속 0개다.
- readback이 없거나 오류이거나 24시간보다 오래되면 실패 안전 방식으로 신규 등록을 0개로 둔다. 마켓 한도 3개 제한 모드도 이 장벽을 우회하지 못한다.
- 서버의 원클릭 오케스트레이터가 작업표를 만들기 전에 한도를 다시 검사한다. 화면이나 API를 우회해도 `idle` RUN을 Shopling 신규등록 큐로 넣을 수 없다.
- 이미 Shopling 등록과 실상품 readback이 끝난 `goods_key`의 마켓전송 재개는 상품코드를 늘리지 않으므로 계속 허용한다.
- 확장프로그램은 Shopling 요금제 화면의 `상품 DB`와 `사용 상품 DB 수 (누적)`을 읽기 전용으로 수집하고, Commerce OS 화면에서 인증된 내부 readback으로 저장한다. Shopling 상품·판매상태는 바꾸지 않는다.
- Production migration 적용과 확장 v0.6.4 배포 전에는 한도 증거가 없으므로 신규등록은 안전하게 차단된 상태가 정상이다.
- 2026-10-30 실화면 검증에서 Shopling 홈은 두 제목을 같은 행에, `10,000 / 11,113` 값을 다음 행의 같은 열에 표시했다. v0.6.5까지의 세로형 파서는 이 표를 읽지 못해 서버 요청이 0건이었다. v0.6.6은 탭·행·열 구조를 보존해 같은 열의 다음 행을 읽으며, 실화면 구조 회귀 테스트로 보호한다. readback 성공 전까지 신규등록 0개 잠금은 유지한다.
- v0.6.6 설치 후에도 운영표와 서버 요청이 0건인 증거를 확인했다. Shopling 홈의 요금제 수치는 최상위 문서가 아닌 내부 프레임에 있으므로, v0.6.7은 `all_frames`로 주입된 수집기가 실제 수치가 있는 프레임에서만 정확한 두 값을 저장하도록 한다. 중첩 프레임 회귀 테스트를 추가하며, 외부 상품·판매상태 쓰기는 계속 0건이다.
- v0.6.7 설치·활성 상태를 Chrome 설정에서 확인했지만 확장 로컬 저장소에는 수집값이 한 번도 생성되지 않았고, Supabase에는 조회만 반복됐으며 쓰기는 0건이었다. v0.6.8은 최상위 문서에서 접근 가능한 중첩 frame 문서를 재귀적으로 읽고, 표가 한 줄로 평탄화된 경우도 파싱하며, `about:blank/srcdoc/data` 계열 하위 문서에는 `match_origin_as_fallback`으로 주입한다. 수집·전송 단계별 진단값을 확장 로컬 저장소에 남기고 Shopling 값이 생기면 열린 Commerce OS 탭이 자동 동기화한다. 운영표 readback 성공 전까지 신규등록 0개 잠금과 외부 상품·판매상태 쓰기 0건은 유지한다.

## 2026-10-30 새 상품코드 물갈이 확정

- 기존 `goods_key` 제목만 바꾸는 재사용 정책은 폐기한다. 매 노출 기회는 새 SEO RUN과 새 selfCode·Shopling `goods_key` 6개로 시작한다.
- 순서는 `60일 검증 무판매 → 기존 6개 품절 → 품절 readback → 기존 6개 삭제 → 삭제 readback → 90일 휴지 → 새 SEO RUN → 새 코드 6개 등록 → 실상품·마켓 readback`이다.
- Product Master 상품 원본과 B코드·옵션 원장은 삭제하지 않는다. 삭제 대상은 검증된 이전 Shopling listing 6개뿐이다.
- 삭제가 불명확하거나 일부 코드만 남았거나 같은 상품의 진행중·확인필요 action이 있으면 자동 재시도하지 않고 멈춘다.
- 새 코드 등록은 최신 Shopling 상품 DB readback으로 6개 슬롯과 안전 여유 12개가 모두 확인될 때만 가능하다. 현재처럼 한도 초과이면 계획과 화면만 준비하고 외부 생성·삭제는 0건으로 유지한다.
- 새 등록 성공은 6개 새 `goods_key`, 6개 고유 selfCode, Shopling 실상품 readback 6/6, 필수 마켓 전송 readback이 모두 맞을 때만 인정한다. 그 전에는 새 시도 횟수를 소비하지 않는다.
